# 1C Client MCP Server

Реализация MCP сервера (Model Context Protocol), который запускается внутри клиента 1С:Предприятие. Проект ориентирован на работу через внешнюю компоненту `AddIn.WebTransport.mcp` и обрабатывает MCP запросы по JSON-RPC.

> [!CAUTION]
> Важно, проект еще не имеет стабильного релиза. Поэтому интерфейсы и внутренние API могут меняться.

## Возможности

- Запуск MCP сервера в клиентском контуре 1С:Предприятия.
- Поддержка инструментов, ресурсов и промптов MCP.
- Транспорт WebTransport MCP через внешнюю компоненту `AddIn.WebTransport.mcp`.
- Реестр обработчиков и унифицированное логирование событий.
- Форма управления MCP в составе расширения.

## Запуск из командной строки 1С

Поведение клиента полностью управляется параметром `/C` при старте
платформы. Формат — пары `key=value`, разделённые `;`. Все ключи
парсятся в `Мсп_ПараметрыЗапускаКлиент`.

### Режимы (`mcpMode`)

| Значение | Что делает |
|---------|------------|
| `ws` | Подключиться WebSocket'ом к менеджеру сессий (`v8-client-session-manager`) и опубликовать в нём свои tools. |
| `http` | Поднять локальный HTTP MCP-сервер (legacy, работает без менеджера). |
| `auto` | Сначала пробует `ws`. Если за `mcp_ws_timeout_ms` менеджер не ответил — падает на `http`. |
| (не задан) | Backward-совместимая ветка: если есть `runMcp=` — поднимается HTTP, иначе ничего не делается. |

### Параметры WS-режима

```text
/C"mcpMode=ws;manager_url=ws://127.0.0.1:4000/sessions;kind=client_drive;mcp_log_level=info"
```

| Ключ | Значения | Назначение | По умолчанию |
|------|----------|------------|--------------|
| `manager_url` | `ws://host:port/sessions` | URL менеджера. | `ws://127.0.0.1:4000/sessions` |
| `client_uid` | UUID | Стабильный идентификатор клиента для soft-reconnect. | автогенерация |
| `kind` | произвольная строка | Namespace публикации tools и бизнес-роль клиента. `vanessa_test_client` — особый: tools не получают префикс. | `1c-client` |
| `corr_id` | произвольная строка | Correlation-id для логов менеджера. | (пусто) |
| `mcp_log_level` | `off`, `error`, `warn`, `info`, `debug`, `trace` | Единый уровень логирования (см. ниже). | `off` |
| `mcp_ws_timeout_ms` | целое, мс | Таймаут WS-handshake'а в `auto`-режиме. | `1000` |

### Параметры legacy-HTTP

```text
/C"runMcp"
/C"runMcp=/tmp/mcp-conf.json"
/C"runMcp=/tmp/mcp-conf.json;mcpPort=123"
```

`runMcp` без значения — используются дефолты. С путём к JSON-конфигу
читаются ключи `port` и `timeout`. `mcpPort` из `/C` имеет приоритет
над `port` из JSON. Дефолты: порт `8080`, таймаут `900`.

```json
{ "port": 8080, "timeout": 900 }
```

## Логирование

Девкит ведёт собственный BSL-лог и одновременно грубо управляет
логированием транспортной компоненты `AddIn.WebTransport`.
Управляющий ключ — один: `mcp_log_level` из `/C`. Применяется до
регистрации провайдеров (через `ПрименитьЛогированиеИзПараметраЗапуска`),
поэтому ни одно «Регистрация провайдера …» не пробивается в UI до того,
как актуальный уровень установлен.

Что происходит на каждом уровне:

| Уровень | BSL-логгер: запись в `%TEMP%\mcp-client.log` | BSL-логгер: дубль в панель `Сообщить` | Транспортная компонента (`tracing` фильтр) |
|---------|---------------------------------------------|---------------------------------------|---------------------------------------------|
| `off` (или ключ не задан) | нет | нет | `off` |
| `error` | только error-сообщения | нет (тихо в проде) | `error` |
| `warn` | warn + error | нет | `warn` |
| `info` | info + выше | да | `info` |
| `debug` | debug + выше | да | `debug` |
| `trace` | всё включая trace | да | `trace` |

Правило показа в панель: `Сообщить` срабатывает только при подробных
конфиг-уровнях (`info/debug/trace`) — при `warn/error/off` логгер не
дёргает UI, чтобы не шуметь в проде.

Транспортная компонента `AddIn.WebTransport` имеет собственный лог
(`%TEMP%\web-transport.log`) с гораздо более детальной диагностикой
WS-handshake'а, ретраев и состояний reconnect'а. BSL вызывает
`session.НастроитьЛогирование(<level>)` сразу после `Новый(...)`, передавая
тот же `mcp_log_level`. Компонента маппит строку на свой `tracing` filter
(поддерживается также EnvFilter-выражение, например
`webtransport=debug,addin1c=info`).

Файлы логов:

- `%TEMP%\mcp-bootstrap.log` — bootstrap-трасировка девкита, пишется
  всегда независимо от `mcp_log_level`. Дублируется в ЖР под событием
  `Мсп.Бутстрап`.
- `%TEMP%\mcp-client.log` — основной BSL-лог, активен на любом уровне
  кроме `off`.
- `%TEMP%\web-transport.log` — лог транспортной компоненты, активен
  на любом уровне кроме `off`.

ЖР клиента (журнал регистрации) дополнительно собирает события
`Мсп.Транспорт.*` (StateChange, SessionRegister, ВнешнееСобытие и т.п.) —
эти записи не зависят от `mcp_log_level` и нужны для пост-фактум
диагностики handshake'а.

```bsl
КонецФункции
```
